# 6. ツール実行基盤

元ページ: https://www.notion.so/31db3ffbf12e81de95c9d727952fc646

## 1. ビジネスコンテキスト
- **目的**: LLM が会話中に必要と判断した操作を、定義済みの安全なツールへ委譲できるようにする。
- **価値**: 自然言語で判断する部分と、実際に副作用を起こす部分を分離できる。
- **現在の設計方針**: tool の定義、実行、結果再投入、UI 反映を疎結合に保つ。whiteboard のような UI 表示更新も `set_whiteboard` tool に寄せ、通常応答は発話と待機の契約へ絞る。Google Calendar のような外部 API 呼び出しは registry から shared client を注入し、SwitchBot は Hub2 状態取得と起動時に取得済みの scene 実行に寄せる。

## 2. ツール実行基盤の責務
この基盤が行うことは 4 つある。
- 利用可能な tool 定義を LLM に渡す
- function call を name で handler に振り分ける
- handler の結果を JSON 化して返す
- その結果を Responses API とフロント UI の両方へ流せる形にする
ポイントは、**tool result は LLM への再投入用でもあり、UI / デバッグ表示用でもある** 点である。

## 3. 論理構造・機能俯瞰
**主要なモデル・コンポーネント**
- **`registry.Registry`**
  - 利用可能な tool 定義と handler の一覧を持つ
  - `Config` から SwitchBot client、Google Calendar client、Diary store、SwitchBot scene 一覧を受け取り、各 tool を生成する
- **`tools.Handler`**
  - 各 tool が実装する共通インターフェース
- **`toolcaller`**
  - `ToolRequest.Name` に対応する handler を選び、実行して `ToolResponse` を返す
  - 起動時に `ContextAware` / `EventEmitterAware` へ context と event emitter を注入する
- **`responsesapi`**
  - Responses API の streaming 出力から tool call を抽出し、tool result を `function_call_output` として再投入する
- **`wschat`**
  - `ToolRequest` / `ToolResponse` を `function_call` / `function_result` として Web UI にも流す
- **`sessionlifecycle`**
  - 通常会話から除外された `write_diary` を、idle timeout 時に強制する側の component
- **shared `CalendarClient`**
  - `conversation` と Google Calendar tools が共有する API client
  - GET キャッシュと invalidate を持つ
- **shared `SwitchBot Client`**
  - Hub2 状態取得と scene 実行 tool が利用する API client
  - 認証署名、時計ずれ補正、API エラー分類を持つ

これらは `registry_test.go` でも未登録であることが確認されている。

## 5. 主要なデータフロー
### シナリオ: function call 実行
1. Responses API の streaming 完了イベントから `responsesapi` が `function_call` を抽出する
2. `responsesapi` が `ToolRequest` を発行する
3. `toolcaller` が handler を name で引く
4. `ToolRequest.Arguments` の JSON を `map[string]any` に decode する
5. `tool.Run(args)` を request ごとの goroutine で実行する
6. 戻り値 map またはエラー map を JSON にして `ToolResponse.Output` へ入れる
7. `responsesapi` は `ToolResponse.Output` を `function_call_output` として OpenAI に再投入する
8. `wschat` は同じ request / response を `function_call` / `function_result` として UI にも流す

`ToolRequest` は `ResponseID`, `ToolCallID`, `Name`, `Arguments` を持つ。`ToolResponse` は `ToolCallID`, `Name`, `ResponseID`, `Output` を持つ。`responsesapi` は tool call ごとに `ToolCallID -> previous_response_id` と `ToolCallID -> RequestID` を保持し、tool result 到着時に対応する previous response へ再投入する。

### シナリオ: Google Calendar tools 実行
1. `registry` が shared `CalendarClient` を `google_calendar_list/create/update` に注入する
2. `toolcaller` が Google Calendar tool の `ContextAware` へ実行 context を注入する
3. tool は引数解釈だけを行い、実際の API 呼び出しは `CalendarClient` へ委譲する
4. `google_calendar_list` は `date` または `time_min` / `time_max` を受け取り、`calendar_id` 省略時は `primary`、`max_results` 省略時は `20` とする
5. `google_calendar_create` は `summary`, `start_time`, `end_time` を必須とする
6. `google_calendar_update` は `event_id` を必須とし、`action=delete` なら削除、それ以外は指定された項目だけ更新する
7. `ListEvents` は 5 分 TTL の GET キャッシュを利用する
8. `CreateEvent` / `UpdateEvent` / `DeleteEvent` 成功時は GET キャッシュが破棄される
9. tool は戻り値を tool 出力形式へ整形して `ToolResponse` を返す

## 6. handler の共通インターフェース
### `tools.Handler`
最小の共通契約。
- `Name() string`
- `Run(args map[string]any) (map[string]any, error)`

### `tools.DefinitionProvider`
LLM に渡す function 定義を返す。
- `Definition() map[string]any`

### `tools.ContextAware`
実行時 context を受け取りたい tool 用。
- `SetContext(ctx context.Context)`
- timer、Google Calendar、SwitchBot Hub2 / scene など、キャンセル可能な処理や外部 API 呼び出しで使う

### `tools.EventEmitterAware`
tool 実行中に非同期で内部 event を発火したい tool 用。
- `SetEventEmitter(func(types.Event))`
- timer の `EventTimerFired` や whiteboard の `EventWhiteboardUpdate` のように、tool result とは別の内部 event を流したいケースで使う

## 7. `toolcaller` の役割
`toolcaller` は単なる switch 文ではなく、**ツール実行のランタイム** である。
担当内容:
- `ToolRequest` を受ける
- handler を lookup する
- 引数 decode を行う
- request ごとに goroutine で実行する
- エラーを JSON 結果へ正規化する
- `ToolResponse` を `EventToolResponse` として downstream へ返す
- stage 起動時に `ContextAware` / `EventEmitterAware` を持つ tool へ実行コンテキストを注入する

エラー方針:
- arguments の decode に失敗した場合は log に出し、空 map として handler を呼ぶ
- 未知の関数名でも panic せず、`{"error": ...}` を返す
- handler 内エラーも同様に JSON に包んで返す
- result の JSON encode に失敗した場合は `{"error":"result encoding failed"}` を返す

## 8. tool result が持つ二重の意味
### 8-1. LLM 継続用の意味
`responsesapi` にとっては、tool result は「前の response にぶら下がる function output」である。`ToolCallID` から保持済みの previous response ID を引き、`input` に `type=function_call_output`, `call_id`, `output` を入れて OpenAI へ再投入すると、assistant が続きを話せる。

再投入時も tools 定義は渡されるため、続きの応答でさらに tool call が返る場合がある。その場合 `responsesapi` は再び `EventResponsesResponse` と `EventToolRequest` を発行する。

### 8-2. UI / デバッグ表示用の意味
`wschat` にとっては、tool result は `function_result` イベントである。管理画面ではそのまま表示できるし、フロントは特定の tool を見て UI state を変えることもできる。
現在 UI state に特別反映しているもの:
- `set_whiteboard`

`set_whiteboard` は tool 実行時に `EventWhiteboardUpdate` を発火し、`wschat` が `whiteboard_update` としてフロントへ流す。`set_volume` は現在 registry に登録されていない。

timer は `schedule_timer` の実行結果とは別に、指定秒数後に `EventTimerFired` を発火する。この event は `ToolResponse` ではなく内部 event として会話側に戻る。

## 9. registry の役割
`registry` は静的な定義一覧と handler 一覧であり、運用上の「どの tool を通常会話で見せるか」を制御する場所でもある。
重要な使い方:
- `Definitions()`
  - 通常会話用 tools 一覧
- `DefinitionsExcluding(names...)`
  - 特定 tool を除外した定義一覧
  - `name` を持つ function 定義だけが除外対象で、`web_search` のような `name` を持たない定義は名前指定では除外されない
- `DefinitionByName(name)`
  - 特定 tool だけの定義取得
  - `web_search` は `name` を持たないため、この API では取得できない
- `Handlers()`
  - `toolcaller` 用の実行マップ
たとえば `write_diary` は通常会話からは除外し、`sessionlifecycle` が idle timeout 時だけ明示的に選ばせる運用になっている。
また、Google Calendar tools については shared `CalendarClient` を registry から注入し、API 呼び出し実装を共有する。SwitchBot scene tool は `Config.SwitchBotScenes` が空でない場合だけ登録され、登録時点の scene 名を `scene_name` の説明に含める。

## 10. 詳細設計
### クラス設計
- `internal/tools/interfaces.go`
  - 共通インターフェース定義
- `internal/tools/registry/registry.go`
  - tool 定義と handler の登録表
  - SwitchBot client、Google Calendar client、Diary store、scene 一覧の注入
  - `web_search` の定義だけ登録
- `internal/components/toolcaller/toolcaller.go`
  - 実行ランタイム
  - `dispatchTool`
    - request ごとに非同期実行を開始する
  - `executeTool`
    - JSON decode -> handler 実行 -> JSON encode を行う
  - `emit`
    - EventEmitterAware tool 用に内部 event を流す
- `internal/components/responsesapi/runner.go`
  - streaming response を処理し、tool request 発行と tool result 再投入を行う
- `internal/components/responsesapi/client.go`
  - Responses API request / streaming / tool output submit を実装する
- `internal/components/wschat/wschat.go`
  - `ToolResponse` を `function_result` として UI へ流す
  - `EventWhiteboardUpdate` を `whiteboard_update` として UI へ流す
- `internal/components/sessionlifecycle/sessionlifecycle.go`
  - `write_diary` 専用 request を出す
- `internal/googlecalendar/client.go`
  - Google Calendar API の共通 client
  - GET cache と invalidate を持つ
- `internal/tools/functions/googlecalendar/tool.go`
  - Google Calendar tools の thin adapter
- `internal/tools/functions/switchbot/hub2.go`
  - Hub2 の温度・湿度・照度取得 tool
- `internal/tools/functions/switchbot/scene.go`
  - 起動時に取得済みの SwitchBot scene を完全一致名で実行する tool
- `internal/tools/functions/switchbot/switchbot.go`
  - SwitchBot API client、署名、時計ずれ補正、エラー分類
- `internal/types/event.go`
  - `ToolRequest` / `ToolResponse` と event kind 定義
- `internal/types/types.go`
  - Responses API request / response / stream chunk などの型定義

### API設計
- 外部 HTTP API は持たない
- OpenAI tools 定義として使われる function tool は次の形式を基本にする
  - `type=function`
  - `name`
  - `description`
  - `parameters`
- built-in tool の `web_search` は `{"type":"web_search"}` として渡す
- tool result は Responses API へ `function_call_output` として返す
  - `call_id` は `ToolResponse.ToolCallID`
  - `output` は `ToolResponse.Output` の JSON 文字列

## 11. 現在の設計上の重要ポイント
- tool の追加は基本的に registry への追加で済む
- tool 実行基盤は「実世界副作用」と「LLM への継続入力」を同じ仕組みで扱える
- `web_search` のように「定義はあるがローカル handler は無い」ツールも扱える
- `web_search` は `name` を持たないため、`DefinitionByName` や `DefinitionsExcluding(name)` の対象にはならない
- `write_diary` のように特定経路だけで使わせる tool も運用可能
- whiteboard のような UI 表示更新も、通常応答契約ではなく tool として統一的に扱える
- Google Calendar のように、複数の利用側から共有したい外部 API は shared client にまとめられる
- SwitchBot の個別 device control tool は現在 registry に存在せず、Hub2 状態取得と任意 scene 実行に整理されている
- `ContextAware` / `EventEmitterAware` は handler 実行ごとではなく、toolcaller stage 起動時に handler instance へ一度注入される
- arguments decode 失敗は toolcaller で fatal 扱いにせず、空 arguments で handler 実行へ進む
