# 6. ツール実行基盤

元ページ: https://www.notion.so/31db3ffbf12e81de95c9d727952fc646

## 1. ビジネスコンテキスト
- **目的**: LLM が会話中に必要と判断した操作を、定義済みの安全なツールへ委譲できるようにする。
- **価値**: 自然言語で判断する部分と、実際に副作用を起こす部分を分離できる。
- **現在の設計方針**: tool の定義、実行、結果再投入、UI 反映を疎結合に保つ。whiteboard のような UI 表示更新も `set_whiteboard` tool に寄せ、通常応答は発話と待機の契約へ絞る。Google Calendar のような外部 API 呼び出しは、必要な tool と会話文脈側で shared client を共有する。

## 2. ツール実行基盤の責務
この基盤が行うことは 4 つある。
- 利用可能な tool 定義を LLM に渡す
- function call を name で handler に振り分ける
- handler の結果を JSON 化して返す
- その結果を Responses API とフロント UI の両方へ流せる形にする
ポイントは、**tool result は LLM への再投入用でもあり、UI / デバッグ表示用でもある** 点である。

## 3. 論理構造・機能俯瞰
**主要なモデル・コンポーネント**
- **`registry.Registry`**
  - 利用可能な tool 定義と handler の一覧を持つ
  - 共有依存を tool に注入する役割も持つ
- **`tools.Handler`**
  - 各 tool が実装する共通インターフェース
- **`toolcaller`**
  - `ToolRequest.Name` に対応する handler を選び、実行して `ToolResponse` を返す
- **`responsesapi`**
  - tool result を OpenAI Responses API に再投入し、続きを生成する
- **`wschat`**
  - `ToolRequest` / `ToolResponse` を `function_call` / `function_result` として Web UI にも流す
- **`sessionlifecycle`**
  - 通常会話から除外された `write_diary` を、idle timeout 時に強制する側の component
- **shared `CalendarClient`**
  - `conversation` と Google Calendar tools が共有する API client
  - GET キャッシュと invalidate を持つ

## 4. 現在の登録ツール
### 生活操作・表示系
- `aircon_control`
- `light_control`
- `blind_control`
- `hub2_get_environment`
- `schedule_timer`
- `set_volume`
- `set_whiteboard`

### 補助系
- `write_diary`
- `google_calendar_list`
- `google_calendar_create`
- `google_calendar_update`
- `web_search`
`web_search` は定義だけ registry に入り、ローカル handler は持たない。つまり、OpenAI Responses API 側の組み込みツールとして使う。

## 5. 主要なデータフロー
### シナリオ: function call 実行
1. Responses API が `function_call` を返す
2. `responsesapi` が `ToolRequest` を発行する
3. `toolcaller` が handler を name で引く
4. arguments JSON を `map[string]any` に decode する
5. `tool.Run(args)` を実行する
6. 戻り値 map を JSON にして `ToolResponse` を返す
7. `responsesapi` はこれを OpenAI に再投入する
8. `wschat` は同じ結果を `function_result` として UI にも流す

### シナリオ: Google Calendar tools 実行
1. `registry` が shared `CalendarClient` を `google_calendar_list/create/update` に注入する
2. tool は引数解釈だけを行い、実際の API 呼び出しは `CalendarClient` へ委譲する
3. `ListEvents` は 5 分 TTL の GET キャッシュを利用する
4. `CreateEvent` / `UpdateEvent` / `DeleteEvent` 成功時は GET キャッシュが破棄される
5. tool は戻り値を tool 出力形式へ整形して `ToolResponse` を返す

## 6. handler の共通インターフェース
### `tools.Handler`
最小の共通契約。
- `Name()`
- `Run(args)`

### `tools.DefinitionProvider`
LLM に渡す function 定義を返す。
- `Definition()`

### `tools.ContextAware`
実行時 context を受け取りたい tool 用。
- timer など、キャンセル可能な非同期処理で使う

### `tools.EventEmitterAware`
tool 実行中に非同期で内部 event を発火したい tool 用。
- timer など、後から `EventTimerFired` を流したいケースで使う

## 7. `toolcaller` の役割
`toolcaller` は単なる switch 文ではなく、**ツール実行のランタイム** である。
担当内容:
- `ToolRequest` を受ける
- handler を lookup する
- 引数 decode を行う
- goroutine で実行する
- エラーを JSON 結果へ正規化する
- `ToolResponse` を downstream へ返す
- `ContextAware` / `EventEmitterAware` を持つ tool へ実行コンテキストを注入する

エラー方針:
- 未知の関数名でも panic せず、`{"error": ...}` を返す
- handler 内エラーも同様に JSON に包んで返す

## 8. tool result が持つ二重の意味
### 8-1. LLM 継続用の意味
`responsesapi` にとっては、tool result は「前の response にぶら下がる function output」である。これを OpenAI へ再投入すると、assistant が続きを話せる。

### 8-2. UI / デバッグ表示用の意味
`wschat` にとっては、tool result は `function_result` イベントである。管理画面ではそのまま表示できるし、フロントは特定の tool を見て UI state を変えることもできる。
現在 UI state に特別反映しているもの:
- `set_volume`
- `set_whiteboard`
`set_whiteboard` は tool 実行時に `EventWhiteboardUpdate` を発火し、`wschat` が `whiteboard_update` としてフロントへ流す。

## 9. registry の役割
`registry` は静的な定義一覧であり、運用上の「どの tool を通常会話で見せるか」を制御する場所でもある。
重要な使い方:
- `Definitions()`
  - 通常会話用 tools 一覧
- `DefinitionsExcluding(names...)`
  - 特定 tool を除外した定義一覧
- `DefinitionByName(name)`
  - 特定 tool だけの定義取得
- `Handlers()`
  - `toolcaller` 用の実行マップ
たとえば `write_diary` は通常会話からは除外し、`sessionlifecycle` が idle timeout 時だけ明示的に選ばせる運用になっている。
また、Google Calendar tools については shared `CalendarClient` を registry から注入し、`conversation` と API 呼び出し実装を共有する。

## 10. 詳細設計
### クラス設計
- `internal/tools/interfaces.go`
  - 共通インターフェース定義
- `internal/tools/registry/registry.go`
  - tool 定義と handler の登録表
  - shared client の注入
- `internal/components/toolcaller/toolcaller.go`
  - 実行ランタイム
  - `dispatchTool`
    - request ごとに非同期実行を開始する
  - `executeTool`
    - JSON decode -> handler 実行 -> JSON encode を行う
  - `emit`
    - EventEmitterAware tool 用に内部 event を流す
- `internal/components/responsesapi/runner.go`
  - tool result を Responses API へ再投入する
- `internal/components/wschat/wschat.go`
  - `ToolResponse` を `function_result` として UI へ流す
- `internal/components/sessionlifecycle/sessionlifecycle.go`
  - `write_diary` 専用 request を出す
- `internal/googlecalendar/client.go`
  - Google Calendar API の共通 client
  - GET cache と invalidate を持つ
- `internal/tools/functions/googlecalendar/tool.go`
  - Google Calendar tools の thin adapter

### API設計
- 外部 HTTP API は持たない
- OpenAI tools 定義として使われる
  - `type=function`
  - `name`
  - `description`
  - `parameters`

## 11. 現在の設計上の重要ポイント
- tool の追加は基本的に registry への追加で済む
- tool 実行基盤は「実世界副作用」と「LLM への継続入力」を同じ仕組みで扱える
- `web_search` のように「定義はあるがローカル handler は無い」ツールも扱える
- `write_diary` のように特定経路だけで使わせる tool も運用可能
- whiteboard のような UI 表示更新も、通常応答契約ではなく tool として統一的に扱える
- Google Calendar のように、複数の利用側から共有したい外部 API は shared client にまとめられる
